# Rulings I made — contrastive-pretrain implementation

In the order I made them, each with what it costs if wrong:

1. **Task 6 fix** — Kept `restore_optimizer_and_scheduler`'s call order unchanged (matches PyTorch's official docs) but corrected a test/docstring that overclaimed it was a "regression test" for a bug that doesn't actually reproduce on torch 2.13. Cost if wrong: a slightly mis-described test comment; zero functional risk.
2. **Task 7 fix 1** — Rewrote a vacuous "doesn't mutate the input" test assertion to one that actually flips on mutation. Cost if wrong: none — test-only.
3. **Task 7 fix 2** — Made `load_frozen_encoder`'s unused `revision` parameter fail loudly instead of silently no-op. Cost if wrong: a caller who tries to pin a revision gets an explicit `NotImplementedError` instead of silently getting `main` — strictly safer either way.
4. **Task 11 fixes 1–5** — Fixed the wrong-interval `data_wait_s` timer, the un-renderable trackio image log, missing test coverage for `run_training`, missing autocast in validation, and missing epoch-boundary checkpointing. Cost if wrong: mostly observability/robustness improvements; low risk.
5. **Task 12 fix** — Added the missing `_FakeTrackioModule` mock (matching existing `data_collection` precedent) so the CLI test doesn't make a real local `trackio.init()` call. Cost if wrong: none — test-only.
6. **Task 13** — Reverted an implementer's fabricated-env-var fix that disabled `torch.compile` in tests (defeating its own regression test), replaced it with a verified real fix (proper CUDA-only device gating + a real, documented torch env var for the actual root cause). This was the one you personally caught and corrected me on.
7. **Final review fix-wave scope** — Bundled only the correctness-blocking findings (projector never checkpointed, epoch-boundary resume bug, memory-probe undercounting, frozen-encoder shape/scale contract, missing resume test) into the one allowed fix wave; deferred efficiency/observability items (val-set re-streaming, incomplete metrics, checkpoint pruning) as tracked follow-ups rather than risk overloading the last fix pass. Cost if wrong: those three items ship as known follow-up work, not fixed now — no correctness risk.
8. **Dataset-resolution mismatch — deliberately NOT fixed, surfaced instead:** the real `objones25/pokemon-frames` dataset stores frames at 2400×2160, not the 160×144 this entire plan (and its spec) assumes throughout. The new shape-validation this fix wave added will now correctly hard-fail on the first real batch rather than silently misbehaving as before. I did not pick a fix (resize-in-pipeline vs. re-extract the dataset) myself — that has real cost tradeoffs and touches an already-approved sub-project's spec. This must be resolved before any real training run, though it doesn't block what just merged (the code is correct and tested against its own stated assumptions).

9. **Dataset-resolution mismatch — resolved.** Added a resize-to-canonical step in `dataset.py`'s `to_pair_transform` (v2 functional API, `TF.to_image` + `TF.resize` to `model.INPUT_HEIGHT`/`INPUT_WIDTH`), matching `augmentation.py`'s existing v2 convention. Verified as a true no-op when the input is already canonical-resolution (empirically confirmed via `torch.equal`), so no existing test needed behavioral changes.
10. **Two parallel-subagent audits (src quality + test suite) of `contrastive_pretrain/`, fix wave applied.** Fixed 9 bounded items under TDD: validation dataloader's inherited `drop_last=True` (could crash an unattended run if held-out val videos total fewer rows than one batch), the untested `val_loss < best_val_loss` publish-skip branch (a flipped comparison would've silently published worse models as "best"), the rate-limit backoff test that only ever exercised a generic transient failure (never the actual 429/quota-delay branch — the same mechanism behind the already-logged HF rate-limit incident), the `data_wait_s` metric misattributing epoch-boundary work (validation + Hub push + checkpoint save) to streaming stalls, plus coverage additions (train/val split filter, CLI `export-frozen-encoder` success path, contact-sheet-once-per-epoch logging) and DRY hoisting of the duplicated `_FakeHfClient`/canonical-frame-builder test fixtures into `tests/conftest.py`. Cost if wrong: all local/test-only or single-purpose runtime-guard changes; independently verified each via reading the actual code path (not just trusting the subagents) and, for the two riskiest, confirmed the new test fails without the fix.
11. **Two findings deliberately NOT fixed at the time, surfaced instead (real cost/scope tradeoffs) — both now resolved, see ruling 12:**
    - `push_frozen_encoder` (`encoder_io.py`) does 3 separate, non-atomic HF Hub commits per publish (confirmed via `inspect` — `HfClient.upload_bytes` is one commit each, no batched multi-file commit in the Protocol). A partial failure mid-publish can leave a repo with weights but no `config.json`, which `_load_frozen_encoder_from_client` then hard-fails on. Fixing this properly means extending `hf_storage.client.HfClient` — shared with `data_collection` — with a `create_commit`-backed batched upload, a cross-cutting interface change I didn't want to make unilaterally.
    - The cosine LR schedule's `T_max` is sized from `_DATASET_ROW_COUNT = 296_000`, the *whole* dataset's row count (already a documented approximation), not the val-excluded training-only stream, so the schedule won't fully anneal by `max_epochs`. A precise fix needs the 2 held-out videos' real row counts, which isn't available without a network call — didn't want to guess a correction factor. Turned out **not** to be low severity: the val split is ~33% of the dataset (see ruling 12), not a rounding error.
12. **Both ruling-11 items fixed, on your go-ahead.**
    - Added `hf_storage.client.AtomicHfClient`, a Protocol narrower than the base `HfClient` (interface segregation — `data_collection`'s per-shard uploads are correctly independent commits and never need this), with `upload_many_bytes` backed by `HfApi.create_commit` + `CommitOperationAdd` (signature verified via `inspect`, not memory). `push_frozen_encoder` now publishes weights + config + latent stats as one atomic commit instead of three independent `upload_bytes` calls — a mid-publish failure now leaves either nothing or everything, never a partial artifact. `data_collection`'s `HfClient` usage and tests are untouched and still pass (interface segregation held).
    - Got the real row counts instead of guessing: read just the `video_id` column (column-pruned, no image bytes) out of all 367 parquet shards of `objones25/pokemon-frames` via `HfFileSystem` + `pyarrow`. Total 296,040 rows across 7 videos, confirmed against the Hub's own `/size` endpoint. The two default `val_video_ids` account for 97,847 rows (D1SrSFZrV7A: 51,967, YW29l3jJXr4: 45,880) — **~33% of the dataset**, not the negligible sliver the "low severity" label in ruling 11 assumed. `_DATASET_ROW_COUNT` (296,000, whole-dataset) is now `_TRAIN_ROW_COUNT = 198_193` (val-excluded), which now correctly sizes the cosine schedule's `T_max` off the stream `run_training` actually trains on. This constant is coupled to `TrainingConfig.val_video_ids`'s default — if that default ever changes, it needs re-deriving the same way (documented inline in `train.py`).
